# 코스콤 한글 보고서 작성

내용만 받아 **코스콤 보고용 표준 양식** 그대로의 `.hwp`를 만든다.
글꼴·간격·표 서식은 원본 템플릿에서 뽑은 블록을 복제해 채우므로 손으로 맞출 필요가 없다.
Claude가 할 일은 두 가지다. **내용을 코스콤 개조식으로 다듬어 `report.json`으로 정리**하고, **렌더러를 돌린 뒤 결과를 확인**한다.

```
사용자 내용 ─(작성 원칙)→ report.json ─(scripts/render.ps1)→ 결과.hwp ─(preview.ps1)→ 확인 → 전달
```

## 준비물

- Windows + Java 8 이상(`java -version`으로 확인)
- Python 3.8 이상: 문서 유형 템플릿 구성 확인(`scripts/presets.py`)에 쓴다. 없으면 그 확인만 건너뛴다.
- (권장) 한컴오피스 뷰어 또는 한글: 결과 확인용. 없으면 열림 확인과 화면 캡처만 건너뛴다.
- 이 스킬 폴더를 `<SKILL>`이라 부른다. 아래 명령은 PowerShell 기준이다.

## 작업 순서

### 1. 보고 유형 고르기

| 유형 | 언제 | 구성 |
|---|---|---|
| **요약보고** `summary` | 1~2쪽짜리 결과·현황·계획·검토 보고. 대부분의 요청 | 제목 박스(결재라인·날짜·부서) → □ 대제목 → ㅇ/-/· → 첨부·참고 |
| **상세보고** `detail` | 표지와 목차가 필요한 기획서·가이드·중장기 계획, 장(I, II…)이 여러 개인 문서 | 표지 → 목차 → I. 장 → [1] 절 → 1. 대제목 → ㅇ/-/· → 별첨 |

사용자가 정하지 않았으면 분량으로 판단한다. 대제목이 5개 이하이고 2쪽 안쪽이면 요약보고로 쓴다. 판단이 애매하면 한 줄로 확인한다.

#### 1-1. 문서 유형 템플릿 고르기

결과보고·계획보고·이슈 보고처럼 자주 쓰는 문서는 **문서 유형 템플릿(프리셋)**이 구성·표·작성 규칙을 정해 둔다. `templates/presets/presets_index.json`을 읽고 요청에 맞는 것을 고른다(목록과 미리보기: `templates/presets/README.md`).

| id | 이름 | 보고 형식 | id | 이름 | 보고 형식 |
|---|---|---|---|---|---|
| `result-report` | 결과보고 | 요약 | `event-plan` | 행사 계획 보고 | 요약 |
| `plan-report` | 계획보고 | 요약 | `weekly-report` | 주간 업무 보고 | 요약 |
| `review-report` | 검토보고 | 요약 | `education-plan` | 교육 기획안 | 요약 |
| `issue-report` | 이슈·장애 보고 | 요약 | `business-plan` | 사업계획서·기획서 | 상세 |
| `meeting-report` | 회의 결과 보고 | 요약 | `proposal` | 제안서·공모전 기획서 | 상세 |
| `trip-report` | 출장 결과 보고 | 요약 | `guide` | 업무 가이드·매뉴얼 | 상세 |
| `visit-report` | 고객 방문 결과 보고 | 요약 | | | |

- 요청의 단어를 각 프리셋의 `keywords`·`summary`와 맞춰 고른다. 사용자가 유형을 말했으면 그대로 쓴다.
- 둘 이상이 맞으면 다음 순서로 가린다.
  - **구체 유형이 일반 유형보다 먼저**: 행사·교육·출장·고객 방문·회의·이슈 프리셋이 맞으면 결과보고·계획보고·검토보고보다 그것을 고른다.
  - **끝난 일인가, 앞으로 할 일인가**: 끝난 일의 결과면 `result-report`. 교육·행사를 앞으로 열 계획이면 `education-plan`·`event-plan`.
  - **결정이 났나**: 하기로 정한 일을 보고하고 승인받으면 `plan-report`. 할지 말지, 어느 안으로 할지 판단을 구하면 `review-report`.
  - **누구와 만났나**: 외부 고객사와의 면담이면 `visit-report`, 사내 회의면 `meeting-report`.
  - **설득인가, 정식 계획인가**: 새 아이디어를 설득하거나 공모전에 내면 `proposal`. 연간·중장기 사업계획처럼 정해진 사업의 정식 계획이면 `business-plan`.
- 위 규칙으로도 두 후보가 갈리지 않을 때만 후보 2~3개를 이름과 한 줄 설명으로 보여 주고 고르게 한다. 어느 것도 맞지 않으면 프리셋 없이 1장의 보고 형식만 정해 쓴다.
- 고른 프리셋의 `preset.md`를 끝까지 읽고 그 구성(대제목·장 순서), 표, 작성 규칙을 따른다. `example.json`은 모양 참고용이다. 예시의 내용을 옮겨 쓰지 않는다.
- `report.json` 맨 위에 `"preset": "<id>"`를 넣는다. 렌더링 뒤 구성 확인(5단계)에 쓰인다.
- 사용자 내용에 프리셋의 대제목에 해당하는 것이 없으면 빈 대제목을 만들지 않는다. 빼고, 전달할 때 무엇이 빠졌는지 알린다.

### 2. 빈 정보 채우기

| 유형 | 필요한 것 |
|---|---|
| 요약보고 | 제목, 결재라인(담당·팀장·부서장의 이름(내선)), 날짜, 부서 |
| 상세보고 | 위 정보 + 본부명, 표지 종류(정식/간략) |

- 날짜를 모르면 오늘 날짜를 쓴다.
- 결재라인을 모르면 **지어내지 말고** `○○○(내선)`으로 둔 뒤, 전달할 때 채워 넣으라고 알린다.
- 부서(상세보고는 본부도)를 모르면 같은 방식으로 `○○팀`, `○○본부`로 두고 전달할 때 알린다. 이것 때문에 작업을 멈추고 묻지 않는다.
- 개인정보에 주의한다. 실명·내선번호가 들어간 파일은 사내 개인정보 보호 도구가 `.pia`로 암호화할 수 있다(실제로 원본 서식 샘플이 이렇게 처리됨). 사용자가 실명을 주면 그대로 쓰되, 시험·예시용 파일에는 가명을 쓴다.

### 3. 내용을 개조식으로 다듬기

`references/writing_guide.md`를 읽고 그대로 따른다. 핵심은 다음과 같다.
- 한 항목 3줄 이내, 명사형 종결(`~ 수립`, `~ 도모`, `~ 실시 예정`)
- 'ㅇ 단계' 중심. 세부는 `-`, 더 세부는 `·`
- 항목 앞에 2~6자 라벨 `(활동 기간)`, `(현황)`
- 원문에 없는 수치·사실은 만들지 않는다

### 4. report.json 쓰기

전체 형식은 `references/report_schema.md`에 있다. 처음이면 예시 두 개를 열어 모양을 본다.
- `references/examples/summary_sample.json`: 원본 Sample(요약보고) 재현
- `references/examples/detail_sample.json`: 원본 Sample(상세보고) 재현

요약보고의 최소 형태:

```json
{
  "type": "summary",
  "title": "11월 정보보호 교육 결과보고",
  "approval": {"담당": "홍길동(1234)", "팀장": "김철수(2345)", "부서장": "이영희(3456)"},
  "date": "2026. 11. 28", "dept": "정보보호부",
  "sections": [
    {"heading": "교육 개요", "items": [
      {"type": "o", "label": "교육 기간", "text": "2026. 11. 3 ~ 11. 21(3주)"},
      {"type": "o", "label": "대상", "text": "전 직원 412명*", "children": [
        {"type": "note", "text": "휴직·파견자 제외"}
      ]}
    ]}
  ]
}
```

항목 `type`은 다음 중 하나다.
- 본문 단계: `o` · `num`(①) · `dash`(-) · `dot`(·) · `note`(*) · `ref`(※)
- 블록: `table` · `box`(노란 강조 박스) · `figure`(그림, 상세보고)

하위 단계는 `children`에 넣는다. 렌더러가 다음을 자동으로 처리하니 직접 넣지 않는다.
- 간격(4·6·8·12pt), 번호(①②, 1. 2., I. II.)
- 라벨 굵게, 자간 조정, 표 행 높이, 목차

표는 `rows` 2차원 배열로 쓴다. 병합은 `"^"`(위 칸과)·`"<"`(왼쪽 칸과), 칸 안 줄바꿈은 `"\n"`이다. 파일은 UTF-8로 저장한다.

### 5. 렌더링

```powershell
& "<SKILL>\scripts\render.ps1" -Json report.json -Out "결과.hwp"
```

PowerShell 대신 Python으로도 같은 렌더러를 부를 수 있다. `"preset"`이 든 report.json이면 구성 확인까지 이어서 한다.

```bash
python "<SKILL>/scripts/render_hwp.py" report.json 결과.hwp
```

출력의 마지막 줄이 `OK <경로>`이면 성공이다. `WARN` 줄은 하나씩 보고 대응한다.

| 경고 | 대응 |
|---|---|
| `3줄 초과(예상 N줄)` | 그 항목을 줄이거나 `-` 하위 항목으로 나눈다(작성 원칙 위반) |
| `마지막 줄 N글자만 남음` | 렌더러가 자간으로도 못 고친 걸침이다. 단어 하나를 빼거나 더해 다시 렌더링한다 |
| `쪽 넘침: N쪽에 글 M줄만 넘어감(약 Xpt)` | 본문(또는 첨부·장)의 마지막 쪽에 몇 줄만 넘어갔다. 그 높이만큼 문장을 줄이거나 항목을 합쳐 앞 쪽에 넣는다. 내용상 두 쪽이 맞으면 그대로 둔다 |
| `[제목] 칸 너비를 넘어 두 줄` | 제목을 줄인다. 요약보고 제목은 한 줄(약 20자)이 원칙이다 |
| `[날짜·부서] … (자간 -15%로도 부족)` | 렌더러가 칸 자간을 먼저 줄여 맞추므로, 이 경고는 정말 길 때만 나온다. 부서명을 줄인다(예: 팀명만). 날짜 표기(`2026. 4. 23`)는 바꾸지 않는다 |
| `[표지 제목] N줄` | 2줄 이내로 줄인다(한 줄 약 13자) |
| `[표] 칸 글자가 칸 폭을 넘어 줄바꿈 N곳` | 칸 문장을 `\n`으로 의미 단위에서 짧게 나눈다. `widths`를 직접 줬다면 빼고 자동 너비로 다시 렌더링한다. 긴 설명이 꼭 필요한 칸이면 그대로 둬도 된다 |
| `그림 빈 공간: N쪽 아래가 약 Xpt 비고 …` | 그림(과 캡션)이 남은 공간에 안 들어가 다음 쪽으로 넘어갔다. 그림 `width`를 줄이거나, 그림 뒤의 짧은 문단을 그림 앞으로 옮긴다 |
| `목차 쪽번호는 … 추정` | 항상 나온다. 6단계에서 실제 쪽과 맞는지 본다 |

참고(점선) 박스 안의 표는 박스 폭에 맞춰 자동으로 줄어든다. 박스 안에도 표를 넣어도 된다.

경고를 고쳤으면 다시 렌더링한다. `ERROR`면 메시지대로 JSON을 고친다(예: 병합 범위가 직사각형이 아님, 그림 파일 없음, 알 수 없는 type).

프리셋을 썼으면 구성도 확인한다.

```powershell
python "<SKILL>\scripts\presets.py" check report.json
```

| 출력 | 대응 |
|---|---|
| `WARN [구성] '…' 대제목 없음` | 사용자 내용에 해당 내용이 있으면 대제목을 만든다. 정말 없으면 그대로 두고 전달할 때 알린다 |
| `WARN [구성] 순서가 프리셋과 다름` | 프리셋 순서대로 대제목(장)을 옮긴다 |
| `WARN [표] '…'에 표가 없음` | 그 대제목의 내용을 프리셋이 정한 표로 바꾼다 |
| `INFO … 자리표시 남음` | 고치지 않는다. 전달할 때 채우라고 알린다 |

- 표지 제목(상세보고) 줄 수는 HY헤드라인M 폭으로 보정해 세지만 경계에 걸린 제목은 어긋날 수 있다. 6단계 캡처에서 표지가 한 쪽에 들어갔는지 본다.
- 표 칸은 한 줄 12~14자 안쪽으로 쓰고 `widths`는 되도록 지정하지 않는다.
- 그림에 캡션이 있으면 렌더러가 그림과 캡션을 한 쪽에 묶는다. 흰 여백이 많은 그림(코쇠 삽화 등)은 넣기 전에 여백을 자른다: `python "<SKILL>/scripts/crop_image.py" 그림.png` → `그림-crop.png`. 출력에 폭 130mm일 때의 높이가 나오니 쪽 안에 들어갈 폭을 고르는 데 쓴다.

### 6. 결과 확인

```powershell
& "<SKILL>\scripts\preview.ps1" -File "결과.hwp" -OutDir "<임시폴더>\shots" -Screens 4
```

- `OK`면 한컴 뷰어가 정상으로 연 것이고, `FAIL`이면 파일이 손상된 것이다. FAIL이 나오면 전달하지 말고 원인을 찾는다.
- 캡처 PNG(`screen01.png`…)를 열어 본다.
  - 3줄을 넘는 항목, 한두 글자만 남은 줄, 쪽 끝에 혼자 남은 제목이 있는지
  - 표 칸 글자가 넘치지 않는지
  - (상세) 목차 쪽번호가 실제 쪽과 맞는지
- Claude Code에서는 이 스크립트를 **샌드박스 밖에서** 실행해야 뷰어 창이 보인다(`dangerouslyDisableSandbox`). 뷰어 창만 캡처하고 데스크톱 전체는 찍지 않는다. 화면 확인에는 이 스크립트만 쓴다(데스크톱 스크린샷이나 마우스 조작은 다른 앱 창을 건드린다).
- 뷰어는 창 하나에 문서를 쌓으므로 스크립트가 한 번에 하나씩만 실행되도록 스스로 기다린다. 파일을 고쳐 다시 렌더링했으면 preview도 다시 실행한다(이전에 연 뷰어는 스크립트가 정리한다).
- 뷰어가 없으면 이 단계를 건너뛰고, 확인하지 못했다고 전달 시 알린다.

줄바꿈 계산은 한컴 뷰어에서 직접 잰 글자 폭과 줄 경계에 맞춘 모델이라 본문 문장은 대부분 화면과 같게 끊긴다. 그래도 표에 없는 특수 기호나 경계에 아주 가까운 문장은 어긋날 수 있다. 쪽 계산도 문단·표 높이를 캡처로 맞춘 모델이라(쪽 끝 위치 오차 ±5pt 안팎) 목차 쪽번호와 쪽 넘침 경고는 대부분 맞지만, 쪽 경계에 아슬아슬하게 걸린 내용은 캡처로 확인한다. 캡처에서 어긋남이 보이면 문장을 다듬거나 JSON 값을 고쳐 다시 렌더링한다(예: `page_break`, 문장 길이).

### 7. 전달

- `.hwp` 경로와 함께 다음을 짧게 알린다.
  - 보고서 구성(대제목·장 목록)
  - 남은 경고와 확인하지 못한 것
  - 결재라인 자리표시가 있으면 그 사실
- `report.json`도 같은 폴더에 남겨 두면 나중에 고쳐 다시 만들기 쉽다.
- 이 PC에 한글 정식판이 없으면 뷰어로만 확인했다는 점을 알린다.

## 지원하지 않는 것 (요청받으면 솔직히 말한다)

- 글자 색, 형광펜, 밑줄 같은 임의 서식(템플릿에 있는 서식만 쓴다)
- 차트 자동 생성(이미지를 만들어 `figure`로 넣는 것은 가능)
- 기존 .hwp 파일을 고쳐 쓰기(내용을 받아 새로 만드는 방식)
- 쪽번호 이외의 머리말·꼬리말
